# Архитектура семейного VPN-портала

Статус: проектное решение, 22 октября 2026 года. Этот документ не подтверждает готовность production-развёртывания.

## Исходные условия

Read-only аудит показал Ubuntu 24.04 x86-64, 1 vCPU, 3,8 ГиБ RAM, около 32 ГиБ свободного диска, systemd и Docker. Существующий контейнер `amnezia-awg2` обслуживает UDP 35473 и интерфейс `amn0`. Его конфигурация, ключи и правила маршрутизации считаются production-данными: портал не изменяет и не перезапускает этот контейнер до отдельного canary-теста, резервного копирования и проверки rollback.

Выбран вариант маршрутизации A: российские ресурсы и локальные сети идут с устройства напрямую, остальной трафик — через зарубежный VPN. Сервер не может восстановить домашний российский IP после попадания запроса в туннель, поэтому split routing и split DNS реализуются клиентом INCY, а не серверным NAT.

## Компоненты

```text
браузер / INCY ──HTTPS──> Caddy :443 ──HTTP loopback──> my-vpn
Telegram API <──HTTPS─── my-vpn (не принимает входящие webhook из Интернета)
                                      │
                                      ├── SQLite + локальные backups
                                      │
                                      └── Unix socket ──> vpn-provisioner
                                                               │
                                                               └── адаптер AmneziaWG
                                                                     │
                                                                     └── существующий amnezia-awg2
```

- **Caddy** завершает TLS для `vpn.akalmaz.tech`, выставляет только 80/443, добавляет security headers и не записывает activation code или конфигурации в access log.
- **`my-vpn`** — один Go-бинарник от непривилегированного пользователя `myvpn`: HTTP API, статический русскоязычный интерфейс, long-polling Telegram-бот, rate limiting, аудит и health endpoint.
- **SQLite** работает в WAL-режиме с `busy_timeout`; файлы БД и backup доступны только `myvpn`. Для одного семейного узла отдельная СУБД и Redis не нужны.
- **`vpn-provisioner`** — маленький локальный адаптер с минимальными привилегиями. Он принимает только типизированные операции `CreateDevice`, `RevokeDevice`, `Status`; произвольные команды, пути и аргументы запрещены.
- **AmneziaWG** остаётся отдельным data plane. У каждого устройства собственная пара ключей и отдельная запись peer; отзыв одного peer не влияет на остальных.
- **INCY** импортирует один полный Xray JSON: персональный VLESS Reality outbound, DNS и правила RU/direct находятся в одном профиле. Это исключает зависимость от отдельного autorouting-профиля при первом запуске.

## Границы доверия

1. **Интернет → Caddy:** полностью недоверенный ввод; ограничения тела, времени, методов и частоты запросов применяются до бизнес-логики.
2. **Caddy → `my-vpn`:** loopback, но HTTP-заголовкам клиента нельзя доверять. Реальный IP принимается только от локального Caddy по заранее определённому заголовку.
3. **Telegram → `my-vpn`:** токен аутентифицирует бота, но авторизация выполняется отдельно по точному числовому `TELEGRAM_ADMIN_IDS`; незнакомым пользователям возвращается нейтральный ответ.
4. **`my-vpn` → SQLite:** БД содержит метаданные устройств, HMAC-коды и аудит, но не должна содержать приватные VPN-ключи после выдачи.
5. **`my-vpn` → provisioner:** локальный Unix socket с владельцем `root:myvpn`, режимом `0660` и проверкой peer credentials. Это единственный разрешённый путь к операциям data plane.
6. **Provisioner → AmneziaWG:** привилегированная граница. Перед включением адаптера документируются точные команды/API конкретной версии контейнера; запрещены `docker exec sh -c` и конкатенация shell-строк.
7. **CI → сервер:** отдельный deploy key, pinned host key, GitHub Environment `production`, атомарный release и ограниченный набор команд. Runtime-секреты не входят в artifact.

## Потоки данных

### Одноразовое приглашение

1. Администратор задаёт подпись родственника и устройства.
2. Сервер генерирует 8 символов Crockford Base32 из CSPRNG (40 бит), показывает код один раз и сохраняет только `HMAC-SHA-256(server_pepper, normalized_code)`.
3. Запись получает TTL 10 минут, счётчик максимум 5 ошибок и состояния `issued → consuming → consumed|expired|revoked`.
4. Активация выполняется одной транзакцией SQLite (`BEGIN IMMEDIATE`): подходящая запись атомарно переводится в `consuming`. Второй конкурентный запрос не может использовать тот же код.
5. Provisioner создаёт уникальные credentials устройства. После успешного результата состояние становится `consumed`; при контролируемой ошибке выполняется компенсирующее удаление созданного peer и безопасный возврат либо окончательный отказ.
6. Приватная конфигурация отдаётся один раз через ответ с `Cache-Control: no-store`; сервер удаляет временный материал сразу после ответа. Повторное скачивание требует нового приглашения.

### Маршрутизация A

- Direct: локальные RFC1918/ULA-сети, доменные суффиксы `.ru`/`.рф`, проверенный дополнительный список банков и государственных ресурсов. Домены не резолвятся в IP для выбора маршрута: это не позволяет зарубежному домену, попавшему на российский CDN-адрес, случайно обойти VPN.
- Proxy: остальной трафик; catch-all должен идти после direct-правил.
- Local/direct DNS обслуживает direct-домены, remote/proxy DNS — прочие. Стратегия доменов не должна сначала резолвить RU-домен через зарубежный resolver.
- Обновление routing assets проходит проверку подписи/хеша, staging-тест и атомарную замену. Последняя рабочая версия сохраняется.
- Если клиентская платформа или версия INCY не подтверждает нужный профиль, UI показывает ограничение и не обещает RU/direct.

## Модель данных

Минимальные таблицы:

- `admins(id, telegram_id, enabled, created_at)`;
- `invites(id, code_hmac, relative_label, device_label, expires_at, attempts, state, created_by, created_at, consumed_at)`;
- `devices(id, relative_label, device_label, provider_ref, public_key, status, created_at, revoked_at)`;
- `audit_events(id, occurred_at, actor_kind, actor_id, action, object_kind, object_id, outcome, metadata_json)`;
- `rate_buckets(key_hmac, window_start, count, blocked_until)`;
- `schema_migrations(version, applied_at)`.

В audit и labels запрещены коды, токены, приватные ключи и полные клиентские конфигурации. IP для anti-abuse хранится как ротационный HMAC, а не открытым текстом.

## Provisioning и существующая Amnezia

Новый data plane — отдельный Xray VLESS Reality на TCP 8443. Go-процесс без
привилегий вызывает только root-owned `reality-helper` через узкое sudoers-правило.
Helper валидирует JSON, атомарно обновляет единственный managed Xray inbound,
проверяет конфигурацию и откатывается при неуспешном restart. UUID хранится только
в защищённом Xray config; SQLite содержит `vless-reality:<device-id>`.

`amnezia-awg2` на UDP 35473 остаётся отдельным работающим rollback-контуром и не
входит ни в provisioning, ни в cleanup. Аудит подтвердил активного peer, поэтому
автоматическое отключение/удаление Amnezia запрещено.

## Развёртывание и rollback

- Артефакт — воспроизводимо собранный статический Go-бинарник и статические assets с SHA-256.
- Релизы располагаются в `/opt/my-vpn/releases/<commit>/`; активный `/opt/my-vpn/current` — атомарно заменяемая symlink.
- Конфигурация и БД находятся вне release: `/etc/my-vpn/` (`0600`, root-owned secrets) и `/var/lib/my-vpn/`.
- Перед миграцией выполняются `sqlite3 .backup` и проверка целостности. Миграции должны быть backward-compatible как минимум с предыдущим бинарником.
- Deploy проверяет `/healthz`, TLS, публичный TCP 8443, реальный Reality egress и production activation/subscription/revoke canary.
- При неуспешном health/smoke symlink возвращается на предыдущий release и сервис перезапускается. БД откатывается только проверенной процедурой; необратимая миграция блокирует автоматический deploy.
- Существующий `amnezia-awg2` не входит в автоматический cleanup и rollback портала.

## Ограничения ресурсов

Для 1 vCPU целевой idle: один Go-процесс, Caddy и существующий VPN; без polling чаще необходимого и без фоновой агрегации метрик. SQLite соединения ограничиваются (`MaxOpenConns=1` для записей), Telegram long polling имеет backoff, журналы ротируются. Фактические idle CPU/RSS, скорость и безопасная ёмкость определяются только измерениями после canary; отсутствие пользовательского лимита не означает безграничную техническую ёмкость.
