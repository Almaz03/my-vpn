# Ёмкость и лимиты

## Наблюдаемая база

На 22 октября 2026 года сервер имел:

| Ресурс | Наблюдение |
| --- | --- |
| CPU | 1 vCPU |
| RAM | 3,8 GiB всего; около 534 MiB занято, 3,3 GiB доступно |
| Swap | 2 GiB; около 29 MiB использовано |
| Диск | 48 GiB; 16 GiB занято, 32 GiB доступно |
| VPN | `amnezia-awg2`, UDP 35473 |

Это моментальный read-only снимок, а не нагрузочное измерение. Пропускная способность порта, CPU на шифрование, latency, traffic quota и число активных клиентов не измерены.

## Три разных числа

Нужно отдельно учитывать:

1. зарегистрированные устройства — записи и отозванные credentials;
2. одновременно подключённые устройства — keepalive/handshake и состояния;
3. одновременно передающие трафик устройства — основной сетевой и CPU-предел.

Владелец не задаёт бизнес-лимит устройств на родственника. Это означает отсутствие фиксированного продуктового лимита, но не бесконечную ёмкость: каждое устройство всё равно получает отдельный ключ/UUID, а сервис применяет глобальные защитные лимиты выдачи и активации.

## Как получить безопасный лимит

1. Зафиксировать idle CPU/RSS/FD/соединения портала, Caddy и VPN не менее часа.
2. Измерить устойчивую скорость одного клиента в обоих направлениях.
3. Добавлять тестовые клиенты ступенями, не занимая весь канал и не затрагивая действующих пользователей.
4. Наблюдать p95 latency, packet loss, CPU steal/load, RAM, swap, FD и ошибки.
5. Определить первый предел по сети, CPU, RAM либо квоте провайдера.
6. Установить эксплуатационный предел не выше 70% измеренного устойчивого значения (запас не менее 30%).

Отдельно проверить портал: конкурентную активацию, SQLite write contention, rate limiter и Telegram polling/webhook. Результаты записываются с версией бинарника и условиями теста.

## Предварительная оценка

1 vCPU — вероятный главный предел при активном шифровании/проксировании, но число пользователей без измерений называть нельзя. 3,8 GiB RAM и 32 GiB свободного диска выглядят достаточными для лёгкого Go-портала и SQLite, однако это не доказывает VPN-ёмкость.

До нагрузочного теста уведомления должны срабатывать по консервативным порогам, например: sustained CPU >80%, available RAM <512 MiB, disk >80%, рост swap и repeated health failures. Конкретные значения уточняются по baseline.
