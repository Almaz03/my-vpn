# Аварийное восстановление

## Цели

До production необходимо согласовать RPO/RTO. Предварительная семейная цель может быть RPO до 24 часов и RTO до 2 часов, но она не считается принятой, пока backup/restore не проверены.

## Что сохранять

- согласованный snapshot SQLite;
- server-side конфигурацию приложения и версии схемы;
- root-only клиентские AmneziaWG-профили и серверный `awg0.conf`;
- Caddyfile и systemd unit без секретных значений;
- манифест релиза: commit SHA, artifact checksum, migration version;
- сведения, достаточные для независимого отзыва каждого устройства.

GitHub Secrets и приватный deploy key в backup сервера не копируются. Секреты не помещаются в репозиторий или artifacts.

## Восстановление портала

1. Изолировать неисправный экземпляр и сохранить диагностические данные без секретов.
2. Подготовить чистую Ubuntu 24.04 либо восстановить текущий сервер из доверенного состояния.
3. Установить проверенный release по checksum.
4. Восстановить конфигурацию с правами `0600` и SQLite из выбранной точки.
5. Проверить целостность БД и миграционную версию до запуска.
6. Запустить приложение на loopback и выполнить локальный health/smoke test.
7. Запустить Caddy, проверить TLS и только затем вернуть трафик.
8. Проверить создание/погашение тестового приглашения и независимый отзыв тестового устройства.

## Rollback релиза

При ошибке нового релиза остановить только портал, вернуть symlink `current` на предыдущую версию и восстановить совместимую копию БД, если миграция необратима. После health/smoke фиксируется incident record. Автоматический rollback нельзя считать рабочим, пока не выполнен преднамеренно неуспешный тест.

## AmneziaWG

`amnezia-awg2` — production data plane. При проблеме портала его не пересоздают. Зашифрованный backup включает серверный config и индивидуальные профили; восстановление перезапускает контейнер только после проверки целостности архива.

## Компрометация

- один client key: отозвать только устройство и выдать новый;
- Telegram token: отозвать через BotFather, обновить secret, перезапустить бот;
- deploy key: удалить public key из `authorized_keys`, выпустить новый отдельный ключ и обновить GitHub Secret;
- host key сервера: проверить причину смены через консоль провайдера, затем обновить `DEPLOY_SSH_KNOWN_HOSTS`; не обходить StrictHostKeyChecking;
- полная компрометация сервера: переустановить из доверенного образа, ротировать все credentials и считать старые client profiles недоверенными.

## Регулярная проверка

Не реже раза в месяц восстановить backup в изолированный каталог/узел, сверить количество записей и audit chain, запустить smoke test без production-трафика и задокументировать время восстановления. Тест не должен использовать действующие одноразовые коды или отправлять private keys в логи.
